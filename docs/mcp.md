# AeroTab MCP

AeroTab exposes its saved connections and terminal-management capabilities to MCP clients such as Cursor and Claude. This is an MCP **server**, not an in-app AI chat client. It reuses AeroTab's SSH authentication, host-key checks, SFTP, and port-forwarding implementation.

## Enable the server

1. Open Settings → MCP.
2. Generate an API token. It is kept in the OS credential store under service `com.aerotab`, account `mcp.apiKey`, not in the settings database.
3. Enable the server and save. The default address is loopback (`127.0.0.1`); port `0` selects a free port.
4. Copy the client configuration shown in Settings. Use the actual listening URL, not port `0` or the wildcard address `0.0.0.0`.
5. Enable only the operation categories needed for the task. Keep the MCP client's own confirmation prompts enabled when starting out.

Local loopback HTTP is permitted because traffic stays on the same host. API-token authentication is required even on loopback. Never post a configuration containing the token into issues, chat logs, or source control.

## Transports

- **Streamable HTTP:** `/mcp` while the desktop application is running. Legacy SSE-only endpoints are not provided.
- **stdio:** `aerotab-mcp`. Protocol output uses stdout; diagnostic logs use stderr. The bridge connects to the desktop endpoint when one is available. Headless operation uses the same saved configuration and permission rules; it cannot open a visible desktop terminal.

The stdio binary is built separately:

```bash
cargo build --release --bin aerotab-mcp
```

Install that binary on the client's PATH, then configure a stdio-capable client:

```json
{
  "mcpServers": {
    "aerotab": {
      "command": "aerotab-mcp",
      "args": []
    }
  }
}
```

For HTTP, use the configuration generated by Settings with its real URL and token. Client-specific HTTP configuration formats differ; an HTTP-capable MCP client is required.

## Permissions and tools

The server is disabled by default. A permission is checked again when each tool is invoked; enabling the generic RPC bridge does not bypass the underlying operation's permission.

- **Connection inventory:** `list_profiles`, `get_profile`, `list_sessions`, `host_stats`. Profile output excludes authentication secrets.
- **Terminal context:** `terminal_export`, `terminal_search`. Output can contain application secrets, so grant access only to trusted agents.
- **File reads:** `list_files`, `read_file`, `get_file_info`, `find_file`.
- **File changes:** `write_file`, `create_file`, `create_directory`, `remove_path`, `rename_path`.
- **Command execution:** `run_command` executes on a separate SSH exec channel with timeout and output limits; it never types probes into an interactive terminal.
- **Session management:** `open_session`, `close_session`, `open_terminal`. Closing a session can affect a user's interactive work.
- **Connection changes:** `upsert_profile`, `delete_profile`.
- **Tunnels:** `tunnel_list`, `tunnel_open`, `tunnel_close`.
- **Remote desktop:** `remote_open` launches the configured system viewer.
- **RPC bridge:** `call_rpc` accepts an explicit method allowlist, not the complete internal command registry.
- **Help:** `help` describes the tools and operation categories.

Local file access is restricted to roots configured by the user. Remote files are accessed through SFTP. File and command outputs are bounded; inspect truncation indicators instead of assuming a returned fragment is complete.

There are no MCP tools for exporting vault entries or keyring secrets. This is not a general data-loss-prevention boundary: a permitted shell command or file read can still access secrets available to its OS user. Use a dedicated restricted SSH account for sensitive environments.

## Context

Start by asking the agent to list AeroTab connections. Refer to stable profile IDs when names are ambiguous. The additional-context field provides operator instructions; treat connection notes, file contents, and terminal output as untrusted data, not permission grants.

## Remote access

Non-loopback binding is an explicit opt-in. Set a bind address, enable remote binding, and supply a TLS certificate and private-key path. Remote binding without TLS must fail closed. Use HTTPS with a certificate trusted by the client; do not disable certificate verification.

A wildcard bind address is not a client URL. Use the machine's reachable DNS name or IP matching the certificate. Restrict access with the OS firewall and a trusted network/VPN. Tokens grant access to the enabled operations; they are not multi-user identities. IP allowlists and mTLS are not provided by this integration.

MCP settings (listener, TLS paths, local roots, and permissions) are device-local and excluded from config sync. Private keys and API tokens are never included in generated public diagnostic output.

## SSH agents and Pageant

Settings → SSH selects `auto`, `system`, `pageant`, or `none`.

- `system` uses `SSH_AUTH_SOCK` on Unix or the OpenSSH agent pipe on Windows.
- `pageant` uses PuTTY's Pageant window-message agent on Windows.
- Windows `auto` tries the system agent first and falls back to Pageant when the system agent is unavailable.
- `none` disables agent authentication.

Pageant is a Windows-only integration. The SSH and MCP paths share agent selection; MCP never receives the private keys. Keep Pageant and AeroTab in the same interactive Windows user session. A locked or missing agent requires operator action.

## Validation

Unit tests cover permission denial, RPC allowlisting, secret redaction, binding validation, and agent selection. Local integration checks should verify initialization, tool listing, wrong-token rejection, token rotation, disabling the server, and permission revocation. Test Pageant with an actual running Windows agent before relying on it for production connections.
